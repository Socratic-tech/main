Guides

Put it online (GitHub Pages)

Create a repo, add this file as index.html, then Settings → Pages → Deploy from branch → main / root. In a minute it's live at your‑name.github.io/repo. One file, nothing to build.

Set the anti‑cheat delay

Open Settings (gear) and pick a delay — 3 seconds is typical. For a guaranteed exact delay, have the players push with &chunked and turn on "Sources are published in chunked mode." Test it before the event: point one feed at a phone stopwatch and confirm the lag is what you expect.

Get a feed to add

Each player's PC or capture publishes to VDO.Ninja and gives you a view link (?view=…) or a stream ID. For rooms, grab the room name and password too.

Add it to the wall

Click Add feed, paste the link or ID, name it (e.g. "Match 1 — Player 1"), pick a bitrate (2500–6000 for 1080p gameplay), Save. The slot sits dark — no bandwidth — until opened.

Watch a feed

Click a slot to go live. Opening another closes the first, so only one stream pulls data. Use Pop out for a floating window if you need to watch two at once (each uses its own bandwidth).

Share the wall

Rename the wall up top, then Share → Copy and send the link. Everyone gets the same feeds and the same delay.

Runs Chrome/Edge best — the broadcast delay relies on Chromium's buffering. Have your officials watch on Chrome or Edge.

The anti‑cheat delay

The wall holds every feed back by a fixed amount before showing it, so nobody watching can relay live information to a player. There are two levels:

  • Best‑effort (default) — just the delay setting, no changes from the players. Works in Chrome/Edge. But the browser treats large buffers as a hint and trims anything much past ~4 seconds, so it's a deterrent rather than a hard guarantee.
  • Exact (chunked mode) — the players publish with &chunked and you flip on the chunked toggle in Settings. VDO.Ninja then buffers with its own system, giving a rock‑solid, frame‑accurate delay of whatever length you set. Chromium‑based browsers / OBS 27.2+ only.
The delay only protects this wall. Anyone who can open the raw ?view=… link sees gameplay live. Keep the source/stream IDs private, password‑protect the streams, and only distribute the wall link.

Always test the real delay before matches start — point a feed at a running stopwatch and measure it. Network conditions and browser versions change the result.

Why this saves bandwidth

Each slot is a still image until clicked — zero connection, zero data. VDO.Ninja is peer‑to‑peer, so video only flows while a viewer is open. The wall keeps one feed live at a time and caps each feed's bitrate, so you never pull every match at once.

What each field does

  • Stream ID / link — the stream to watch; a pasted vdo.ninja link is parsed for you.
  • Video bitrate cap — the most data a feed may pull, in kbps.
  • Codec — leave Auto. VP9/AV1 compress better; H264 is most compatible.
  • Audio — off by default; on for the caster feed.
  • Room + password — only for feeds inside a VDO.Ninja room.

Solo streams vs rooms

A solo stream is just an ID → ?view=ID. A room feed adds room + scene → ?room=NAME&scene&view=ID. Leave the Stream ID blank on a room feed to show the room's whole layout in one slot.

Ways to view

  • In‑page viewer — the default click. One at a time, cleanest bandwidth.
  • Pop out — a separate floating window; open several for a true multiview, each using its own bandwidth.
  • New tab — full‑tab view.

Sharing & privacy

  • The share link holds your feed names and stream IDs, packed into the URL — no server.
  • Video travels device‑to‑device; it does not pass through your GitHub page.
  • Opening a shared link replaces the wall stored in that browser — Export JSON first to keep the old one.

Troubleshooting

  • Delay seems short / inconsistent — you're in best‑effort mode. Have players push &chunked and enable chunked mode; watch on Chrome/Edge.
  • Black screen — the player is offline, the ID is wrong, or it needs a password.
  • Nothing connects — must be HTTPS (GitHub Pages is). School/venue firewalls sometimes block WebRTC.
  • Pop‑out blocked — allow pop‑ups, or use the in‑page viewer.
  • No sound — audio is off per feed by default; edit the feed to enable it.
Needs a modern Chromium browser (Chrome or Edge) served over HTTPS. That's the requirement for the delay to behave.
